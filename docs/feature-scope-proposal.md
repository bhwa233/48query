# 48query 功能范围方案

> 2026-10-19 范围变更：停止采集录播，录播、弹幕和榜单不再属于当前计划。本文保留为历史讨论稿；最新范围与待 review 选项见 [图文采集评审稿](text-image-collection-review.md)。

> 整理日期：2026-10-18
>
> 状态：方案讨论稿，未进入业务代码实现。
>
> 产品约束：每日跑批，次日更新；页面只查询本站已保存的数据，不在用户访问时调用口袋接口。

## 1. 产品定位

48query 适合定位为“口袋48历史消息、录播弹幕和公开榜单统计站”，核心价值是把已经采集并经过统一口径处理的数据做成可查询、可比较的历史档案。

它不应承诺实时直播监控，也不应把弹幕、贡献榜或每日一次的状态快照解释成真实在线人数、完整消费金额或全体粉丝行为。页面必须同时展示数据截止日期、采集覆盖范围和最近批次状态。

当前尚未完成 danmakus 的实际页面核对，因此下面是根据 48tools、yaya_msg 和现有能力整理出的可行产品范围，不等同于对 danmakus 已有功能的逐项复刻。

## 2. 推荐的功能分期

### 2.1 首期：历史统计与检索

首期只使用可以按历史记录补采、并且适合每日增量更新的数据。它构成一个完整可用的统计站，不依赖实时长连接。

| 模块 | 首期功能 | 统一口径 |
| --- | --- | --- |
| 首页 | 昨日消息量、活跃成员数、公开回复数、已发现录播数、已解析弹幕数、批次更新时间 | 统计日按北京时间；批次未完成或覆盖不足时显示“部分覆盖”，不显示为零 |
| 成员 | 成员搜索、团体／队伍筛选、成员详情入口 | 目录字段代表当前资料；历史记录不根据当前队伍倒推历史队伍 |
| 成员统计 | 本人消息趋势、活跃天数、消息类型分布、发送时段、媒体数量 | “本人消息”要求发送者稳定 ID 与成员 ID 匹配；房间内其他成员和粉丝消息单独计数 |
| 消息检索 | 关键词、成员、日期、消息类型、发送者类型筛选 | 只检索本站已采集记录；结果显示原始发生时间和数据来源范围 |
| 图片与媒体 | 图片时间线、音频／视频消息记录、消息详情 | 媒体源地址可能失效；是否保留本站副本由存储方案另行确定 |
| 录播 | 成员、日期、类型、标题筛选；场次详情 | “场次数”指已从接口发现的录播记录，不等于全部实际开播次数 |
| 弹幕 | 单场弹幕总数、按分钟密度、关键词检索、昵称检索 | 弹幕解析只有相对时间、昵称和文本；昵称数不命名为独立用户数 |
| 榜单 | 本人消息量、活跃天数、公开回复记录数 | 只在相同统计日期和相同覆盖范围内比较；未完整覆盖的成员要标记 |

首期不放入粉丝数、直播贡献榜和直播时长等字段，除非最小接口验证已经确认其含义和历史可查范围。这样可以避免页面先上线一批名称明确、含义却不稳定的指标。

### 2.2 第二期：验证后扩展

以下功能有源码线索，但需要先完成代表性账号、不同年代记录和权限条件下的实测。验证通过后可以加入每日批次。

| 功能 | 预期呈现 | 必须先验证的事项 |
| --- | --- | --- |
| 粉丝数快照 | 成员粉丝数时间线、相邻采集日净变化 | 稳定字段、数值含义、登录要求、是否会回写历史 |
| 鸡腿／乱斗榜 | 期次详情、成员排名、贡献值走势 | 期次 ID、真实日期、缺失期次、榜单是否最终结算 |
| 单场直播贡献榜 | 该场接口实际返回的排名和贡献值 | 历史场次可查性、返回是否截断、数值单位、是否为最终值 |
| 动态档案 | 动态列表、发布时间、发布量 | 列表分页、删除和可见性；点赞／评论计数需独立快照 |
| 公演档案 | 公演列表、成员关联记录 | 关联记录是否代表实际出演，不能直接命名为出勤率 |
| 录播时长 | 可靠起止时间下的场次时长 | 开始／结束字段、跨午夜场次、中断和剪辑影响 |
| 粉丝房间发言 | 采集范围内的发言量和发言昵称 | `list/all` 权限、完整历史、稳定用户 ID、分页边界 |

这些功能在验证前可以保留为数据模型和批次任务的预留项，但不应出现在首期正式排名中。

### 2.3 产品层扩展：不增加上游采集压力

收藏成员、收藏场次、保存筛选条件、分享查询链接和显示批次状态等功能只依赖本站数据，可以在首期页面稳定后加入。它们不改变每日跑批策略，也不需要实时接口。

数据导出需要单独决定范围。建议先支持当前页面的汇总结果导出，不默认提供全站原始消息和媒体的批量下载。

## 3. 指标定义

首期指标必须使用固定定义，页面标题、接口字段和数据库汇总都沿用同一套名称。

| 指标 | 定义 | 不应解释为 |
| --- | --- | --- |
| 本人消息数 | 统计日内，发送者稳定 ID 等于成员 ID 的消息条数；是否包含系统通知由消息类型白名单决定 | 成员在线时长或打开 App 次数 |
| 房间消息数 | 统计日内出现在该成员房间的消息条数，发送者可以是成员、其他成员或粉丝 | 该成员本人发言数 |
| 活跃天数 | 选定时间范围内至少出现一条符合口径消息的自然日数量 | 连续在线天数 |
| 公开回复数 | 已采集且被识别为公开回复／礼物回复／公开翻牌的记录数 | 成员处理的全部提问数 |
| 媒体消息数 | 具备图片、音频或视频内容的消息数；同一消息内多媒体是否按资源数另列 | 图片、音频、视频总量，除非页面明确标注统计单位 |
| 录播场次数 | 已发现并保存的录播记录数 | 实际全部直播场次 |
| 弹幕数 | 成功下载并解析的录播弹幕文本行数 | 观看人数、独立观众数或完整弹幕用户数 |
| 昵称发言数 | 在指定场次或范围内按原始昵称分组的弹幕行数 | 准确的用户发言榜 |
| 粉丝净变化 | 两个已保存粉丝数快照的差值 | 该日新增关注人数 |
| 贡献值 | 接口返回的榜单字段原值或明确单位后的值 | 直播总流水、人民币收入 |

所有汇总都按 `Asia/Shanghai` 划分自然日。场次跨午夜时，首期按开播日归属；若没有可靠开播时间，则不把弹幕或媒体强行拆到两个日期。

## 4. 页面与数据状态

建议每个页面都显示以下状态信息：

- 数据截止日期，例如“数据更新至 2026-10-17”。
- 最近批次完成时间和批次状态。
- 当前成员或场次的最早可用记录日期。
- 是否仍有历史补采任务、失败任务或待解析弹幕。
- 统计是完整覆盖、部分覆盖还是仅有快照。

“暂无数据”“尚未采集”“采集失败”和“统计值为 0”必须分开。比较和排名应默认排除覆盖范围不一致的对象，或在结果中明确标出覆盖差异。

## 5. 每日跑批的产品行为

每日批次按以下顺序产生次日数据：

1. 更新成员目录和房间映射，记录目录版本。
2. 从每个房间的上次进度继续读取新增消息，直到覆盖上次成功位置；一页不足以覆盖时继续翻页。
3. 发现新增录播并尝试获取弹幕文件；文件延迟生成的场次进入后续重试队列。
4. 保存已验证的榜单和状态快照。
5. 回查近期日期，修订迟到的录播、跨午夜场次、动态计数和榜单结算结果。
6. 重新计算受影响日期的汇总，发布本批次覆盖报告。

用户访问只读取上一批及历史批次的结果。采集失败时沿用上一版已确认数据，并在页面标出当前批次失败，不用空结果覆盖旧数据。

## 6. 明确不纳入当前版本的功能

以下功能与“每日跑批、次日更新”的模式不匹配，或者现有数据不能支持可靠结论：

- 实时直播状态、开播提醒和实时弹幕看板。
- 实时在线人数曲线、峰值在线、真实独立观众数。
- 跨场次独立弹幕用户数和准确的粉丝用户画像。
- 完整礼物流水、全站消费榜和真实收入榜。
- 全体粉丝翻牌回答率、平均回复耗时和全部翻牌收入。
- 已结束且平台未保存的房间上麦音频回放。
- 开始采集之前每天的粉丝增减和榜单过程变化。

这些项目不是页面暂时没有做，而是当前采集模式和证据不足以保证其含义。若将来平台提供可补取的历史数据，应重新评估并单独标注数据来源。

## 7. 进入实现前的确认项

在开始编写业务代码前，建议确认以下默认选择：

1. 首期采用“成员本人消息 + 房间消息分开统计”的口径。
2. 首期页面只展示前一日及更早的已完成批次，不展示实时状态。
3. 首期纳入消息、图片、录播、弹幕、成员统计和基础榜单；粉丝、贡献榜、动态互动数列为验证后扩展。
4. 比较和排名使用共同覆盖时间范围，覆盖不足的对象显示警告。
5. 原始消息保留公开展示所需字段，粉丝用户标识不直接作为公开用户画像使用。

确认以上范围后，再单独制定数据库、采集任务、存储和页面实现方案。当前文档不授权开始业务代码实现。
