## 3. 为什么会反复报错

### 3.1 修复以单个症状为单位，协议适配尚未覆盖真实端点

`apps/collector/src/pocket48-content.ts:42` 的列表解析仅接受一组数组字段，或仅含 `nextId=0` 的特例。最新 posts 的未知结构触发这里的保护。

`apps/collector/src/pocket48-source.ts:768` 遇到重复非终止游标会报错，只为 album/post_images 的“原始列表为空且游标回显”作了豁免。最新错误发生在 room_posts 和 room。

失败日志没有响应字段结构、原始列表长度和请求/响应游标关系，因此不能确认 posts 是空列表变体、字段变更还是异常响应，也不能确认重复游标是正常空尾页还是真正停滞。直接失败点已确认，精确上游响应语义仍待补证。不能直接把所有未知结构当空、所有重复页当结束。

### 3.2 核验缺口也会累计三次，然后长期停采

`run.ts:48` 对除 SourceRequestSkipped 之外的核验缺口也递增 failureCount；三次后保存 skippedAt，`run.ts:90` 后续跳过整个来源。历史正文无法核验也可能因此停止新增首页读取。

当前恢复需要显式 `--retry-skipped`。定时工作流没有该参数，周任务的 `--retry-unverified` 只重查身份，不解除内容来源隔离。失败次数下降、CI 变绿可能只是请求不再执行，不能证明恢复。

### 3.3 错误分类和重试策略在入口间不一致

来源请求没有统一有限重试，只有 HTTP 502 被归为临时跳过。429、503、504、网络超时、名单刷新和首次初始化的处理不一致。入库和媒体下载已经有部分重试能力，应在现有实现上统一行为。

源码另有一个本批日志尚未观察到的风险：HttpIngestStore 将所有写请求视为可重放，但 `/ingest/progress` 使用 revision 条件更新。若服务端已提交而响应丢失，再用旧 revision 重试会返回 409。必须区分“本次写入已成功”和“另一进程确实更新过进度”，不能取消 CAS 或把所有冲突吞掉。

### 3.4 缺少独立的新鲜度与完整性验收

最新汇总：候选 960、身份已核验 411、身份未核验 42、身份失败 1、尚待身份处理 506，标记 scopeComplete 的仅 5。身份核验、发生过采集、范围历史完整不能互相替代。

sourceFailures=240 来自成员进度错误汇总，不是本轮新增 240 次失败；本轮实际 source_failed 为 12 次。

最新两轮增量阶段尝试 38/40 名、历史阶段 12/8 名。虽然 cron 配置每两小时触发，最近实际触发间隔约 4–7 小时，不能承诺每名成员两小时更新。GitHub 官方明确 schedule 可能延迟或在高负载时丢弃排队任务；周重查又依赖运行时刚好处于周日 00 点，延迟可能错过该窗口。

## 4. 已确认的运行规则

用户已确认：单来源暂时异常允许降级继续，保存缺口并按期重试；持续失败、鉴权或写入失败仍标红。运行健康、数据完整性和数据新鲜度分别报告。

用户已确认：连续失败后隔离的来源允许到期自动探测恢复，限制每轮探测量，人工明确停用的来源保持停用。对应实现见第 8 节。

用户已确认：同一成员、同一来源连续 3 轮实际尝试失败后标红；同一轮内的重试只计一次，未轮转到不计，真实成功后清零。该阈值适用于允许暂时降级的来源故障，鉴权、持久化及协议故障仍按关键错误规则处理。

用户已确认：隔离后首次等待 2 小时探测；继续失败则依次等待 6、12、24 小时，此后每 24 小时探测。间隔从本次失败探测结束后计算，到期后由下一轮任务执行；成功后恢复正常采集。

用户已确认：对已启用增量采集的成员和来源，24 小时未成功读取则警告，48 小时则标红。协议确认的正常空列表也算成功，成员没有发布新消息本身不触发报警。

新鲜度按最近一次成功的增量读取时间计算；历史补采不刷新增量新鲜度。启用后尚未成功读取的来源从启用时间计算，首次覆盖进度另行展示。人工停用的来源保留停用原因，不按正常增量调度要求处理。报警阈值为验收目标，是否能在全团范围满足还需结合实际限速、吞吐和轮转验证。

## 5. 完整修复顺序与验收

### A. 先补证真实响应，再修协议

1. 使用现有 dry-run/diagnostics 对最新失败成员，限定 posts、room_posts 两类来源；另重放 149356907 的 room 历史游标。
2. 仅记录端点、HTTP/业务状态、字段名和类型、原始列表长度、请求游标是否回显等结构证据；不记录正文、媒体 URL、凭证或自由文本错误。
3. 按端点明确区分正常数据、已确认空列表、确定结束、重复非空页、未知结构。仅为有现场证据的空尾页结束分页；未知结构及非空重复页继续保留游标并报告协议错误。
4. 建立脱敏响应回放，验证空尾页恢复、非空重复页保护、作者核验及 2026-01-01 北京时间下界。

审查时本机缺少 Pocket48 凭证，原日志也未开启 source_schema。实施阶段已通过 CI 中的只读诊断补齐真实响应与游标关系，运行编号见第 8 节。

### B. 统一错误与退出语义

| 类别 | 行为 | 完整性与退出规则 |
| --- | --- | --- |
| 页/时间预算到期 | 保存进度、后续续采 | 预算到期本身不是故障；仍评估持续故障和新鲜度，不以有界结束覆盖已有告警 |
| 上游 429、502/503/504、网络超时 | 服从预算和限速的有限重试；随后仅降级该来源 | 原游标保留；暂时异常不标红，持续失败达到阈值后标红 |
| 名单短时不可用且有可靠旧名单 | 继续使用并展示快照年龄 | 刷新仍欠账，过期到阈值后标红 |
| 无可靠名单可初始化 | 明确初始化失败 | 不能用空名单成功结束 |
| 鉴权、持久化、真实进度冲突 | 保留原错误并失败 | 立即标红，不越过未提交页 |
| 未知协议、非空重复页、缺分页边界 | 隔离错误来源，其他独立来源可继续 | 保留游标，作为协议故障标红，不伪造完整 |
| 历史房间/目录暂时不能核验 | 保留待核验状态，安排低频复查 | 不因缺口本身标红，不宣称完整 |
| 媒体暂时失败 | 保留补传记录，继续独立正文采集 | 媒体单独降级，持续失败标红 |
| 启用的增量来源长期未成功读取 | 基于持久化成功时间评估，并在轮转中优先处理超龄来源 | 24 小时警告、48 小时标红；正常空列表算成功 |

复用现有错误类型、CollectionBudget 和 HttpIngestStore。持续失败按已确认规则，在同一成员、同一来源连续 3 轮实际尝试失败后标红；轮内重试不重复计数，未轮转到不计，真实成功后清零。新鲜度独立按 24 小时警告、48 小时标红，避免靠低频探测掩盖长期无更新；预算到期、未轮转到或本轮未发出请求都不能重置最近成功时间。

### C. 将隔离与恢复闭环，并补偿已有缺口

按已确认的自动恢复规则，实施时执行：

1. 分开传输故障、协议故障和历史核验待补；历史核验缺口不连带冻结新增首页。
2. 为可恢复隔离保存 nextRetryAt、最近故障时间及原因，到期用原游标探测；隔离后首次间隔 2 小时，继续失败依次退避 6、12、24 小时，之后维持 24 小时间隔。间隔从失败探测结束后计算，到期后由下一轮任务执行，成功后恢复正常轮转。
3. 每轮为恢复探测保留有限预算，避免重试挤占增量和历史任务；人工暂停独立保留。
4. 先只读列出旧 skippedAt，区分已修复缺陷、历史证据不足和人工停用，再分批恢复；不全量清空游标或失败状态。
5. 用持久化到期时间安排身份周复查，替代运行时必须刚好落在周日 00 点的判断。

优先兼容现有 sources JSON 和旧记录。若最终必须新增表迁移，先本地验证；远程 D1 迁移仍需明确授权。

### D. 按请求语义处理重试

来源和名单统一有限重试、退避及可用的 Retry-After；所有实际发出的 Pocket48 请求继续遵守 5 秒限速，等待和响应读取均服从总预算。

### E. 补上 Cloudflare 安装阶段的恢复能力

本次故障在自动安装阶段，发生于用户 build command 之前；只在当前项目 build command 后面追加重试覆盖不到失败点。

建议继续使用 Git 集成和当前固定版本，将依赖安装变成可观察、可有限重试的独立步骤。Cloudflare 官方支持 `SKIP_DEPENDENCY_INSTALL=1` 后在自定义命令中安装依赖：实施时先在受限验证构建中确认 pnpm 引导下载也进入受控步骤，再对网络超时作有限退避重试，保留 `--frozen-lockfile`。平台工具准备阶段仍可能独立失败，此类失败只能在确认尚未部署且没有更新提交后有限重试整个构建，不能靠项目脚本保证完全消除。

不因一次网络超时改 pnpm 版本、删除锁文件、清空依赖缓存或切换到手工发布。真正依赖不兼容、编译、审计和测试失败不应被这类网络重试吞掉。Web/API 的部署结果分别核对，构建恢复不代表采集响应协议已修复。
