# 口袋48 消息归档站 · 实现方案

> 2026-10-19 更新：本文保留为早期方案。当前范围与验收以 [图文采集评审稿](text-image-collection-review.md) 为准；下文样本数字不能作为当前账号的验收证据，房间映射、图片有效期、历史覆盖和请求频率等结论不能推广到全部房间。技术实现沿用当前 Workers／D1，不按本文切换部署架构。

> 目标：公开可访问的网站，展示全团约 250–350 位在册成员的房间消息与图片（不含视频）。
> 本文所有数字均来自 2026-10-18 的实测，不是估算。

---

## 一、已验证的事实

P0 探测已经把这些问号消掉了：

| 项目   | 结论                                                                |
| ---- | ----------------------------------------------------------------- |
| 鉴权   | 手机号 + 短信验证码换 token，`pa` 头由 WASM 签名，已跑通                            |
| 房间映射 | `roomId.json` 直接给出 528 条成员的 `serverId` / `channelId`，无需调用 jump 接口 |
| 历史回溯 | 可用。每页实际返回 16–50 条（`limit` 参数被服务端忽略），约 **4.36 天/页**                |
| 图片   | **永久链接，无防盗链**，裸 GET 返回 200                                        |
| 风控   | 5s 间隔连续 50 次请求，0 失败，平均响应 157ms                                    |
| 去重键  | `msgIdServer`，实测 2074 条全部唯一                                       |

实测样本（宋昕冉 6738，50 页）：

- 2074 条，覆盖 218 天
- 类型：TEXT 79.7%、EXPRESSIMAGE 6.5%、IMAGE 6.3%、LIVEPUSH 3.3%、AUDIO 1.5%、REPLY 1.4%、VIDEO 0.7%、GIFTREPLY 0.6%
- 单条消息 JSON 平均 520 字节；2074 条文本合计仅 12 KB
- 图片 278 条，其中 144 条带 size，累计 163.9 MB，**单张平均 1165 KB**

## 二、四个关键设计决策

### 1. 不做 NIM 长连接，用轮询

这是整个方案里最大的一处简化。yaya_msg 那套网易云信私有 TCP 协议（手写 packet、LBS 寻址）原本是必须移植的，但既然历史接口能翻页、图片又是永久链接，**实时性就不再是硬需求**。

做法：每个成员每 N 分钟拉一次第 1 页，用 `msgIdServer` 去重。

间隔怎么定：实测顶流成员日均 6 条、高峰约 20 条/小时，而一页能装 50 条。所以 **10 分钟一轮完全不会漏**，即使高峰期也够。真正密集的房间可以单独加密到 3 分钟。

省掉的成本：NIM 协议移植、长连接保活、断线重连、多账号连接数限制。

### 2. 图片延迟下载 + WebP 转码

图片链接没有签名参数，什么时候下都行。所以采集器只管存 URL，图片由一个独立队列慢慢补。

必须转码：原图平均 1.1 MB（手机原图 3552×4736），网页根本用不上。转成 1600px 宽的 WebP 约 150–250 KB，**省 80%**。

按单成员 3 年约 700 张算：原图 800 MB/人，转码后约 150 MB/人。250 人就差了 160 GB。

### 3. 采集与展示彻底分离

采集器是个独立的 Node 进程，只写库；Web 只读库。两者不共享运行时，采集挂了网站照常访问。

这样也方便：采集器可以随便重启、限速、暂停，不会影响在线服务。

### 4. SQLite 起步，预留 PG 迁移

350 个房间 × 1 万条约 350 万行，SQLite 加上索引完全跑得动，而且零运维、备份就是拷文件。

但公开站有并发读和全文检索需求，**建议直接上 PostgreSQL**（单机 Docker 即可）。如果只是先跑通，SQLite 也够，字段设计保持不变，后期换连接串就行。

## 三、数据模型

四张核心表。

### members

成员与房间映射，来自 `roomId.json`。

| 字段                     | 说明                       |
| ---------------------- | ------------------------ |
| id                     | 成员 ID（目录里的 `id`），主键      |
| owner_name             | 姓名                       |
| pinyin                 | 拼音，用于搜索                  |
| group_name             | 所属团体                     |
| team                   | 队伍 / 期数                  |
| server_id / channel_id | 房间标识，消息接口必填              |
| live_room_id           | 直播房间号，暂不用                |
| status                 | active / gone，失效房间标 gone |
| last_sync_at           | 上次增量同步时间                 |

`status` 很重要：目录里 528 条有大量已毕业或关闭的房间，第一次探测到「频道不存在」就标 `gone`，之后不再请求。

### messages

主表，字段与接口返回一一对应。

| 字段                                      | 说明                              |
| --------------------------------------- | ------------------------------- |
| msg_id_server                           | **唯一索引 / 去重键**                  |
| member_id                               | 关联 members                      |
| msg_time                                | 毫秒时间戳，建索引（翻页和排序都靠它）             |
| msg_type                                | TEXT / IMAGE / EXPRESSIMAGE / … |
| body_text                               | 纯文本内容（TEXT 类）                   |
| body_json                               | 原始 bodys，图片类存结构化 JSON           |
| sender_id / sender_name / sender_avatar | 从 `extInfo.user` 解出来            |
| sender_level / sender_role              | 粉丝等级、角色，用于展示区分                  |
| has_media                               | 布尔，是否有图，建索引供图片墙用                |

索引组合：`(member_id, msg_time desc)` 用于时间线分页；`msg_id_server` 唯一；`has_media` 单独建部分索引。

### images

图片表，与 messages 一对多（一条 IMAGE 消息对应一张）。

| 字段                          | 说明                        |
| --------------------------- | ------------------------- |
| id                          | 自增                        |
| msg_id_server               | 关联消息                      |
| src_url                     | 口袋原图地址（永久）                |
| md5                         | 接口自带，可用于跨成员去重（同一张图被转发时）   |
| size_bytes / width / height | 接口自带，无需探测                 |
| ext                         | jpg / gif / png           |
| stored_key                  | 对象存储里的 key，转码后写入          |
| status                      | pending / stored / failed |

`md5` 是个好用的字段：不同成员之间转发同一张图很常见，靠它去重能省不少存储。

### sync_state

每个成员的翻页游标。

| 字段               | 说明             |
| ---------------- | -------------- |
| member_id        | 主键             |
| oldest_next_time | 历史回溯游标，翻到哪存哪   |
| newest_msg_time  | 最新一条的时间，用于判断增量 |
| history_done     | 是否已翻到最早        |
| last_error       | 最近一次失败原因       |

有了这个，历史灌入可以断点续传，进程随时重启不丢进度。

## 四、采集流程

### 历史灌入（一次性）

对每个 `active` 成员，从 `nextTime=0` 开始循环翻页，直到 `nextTime` 不再推进或返回空页，每页间隔 5 秒。

写入策略：先 upsert messages，再更新 `sync_state.oldest_next_time`。每页一个事务，保证崩溃后能接着跑。

按实测速率：单成员 250 页约 21 分钟，350 个成员串行需要 5 天。想更快就缩间隔，**2 秒是否安全还没测**，这是唯一待验证项。

### 增量同步（长期）

每 10 分钟一轮，对每个 `active` 成员拉第 1 页，按 `msg_time > newest_msg_time` 过滤后写入。

这里要防一个坑：如果某成员突然爆发式发言，一页 50 条装不下 10 分钟的量。应对是——当发现第 1 页的最早消息时间仍大于 `newest_msg_time`，说明有缺口，自动往前多翻一页补齐。

### 失败处理

| 情况        | 处理                       |
| --------- | ------------------------ |
| `频道不存在`   | 标 `status = gone`，停止后续请求 |
| token 失效  | 暂停采集，告警，等人工重新登录          |
| 网络错误      | 指数退避重试 3 次，仍失败则跳过本轮      |
| 触发限流（若出现） | 全局暂停 30 分钟，间隔翻倍          |

## 五、图片管道

三个独立阶段，解耦运行：

1. **发现**：采集器扫 `has_media = true` 且 `images.status = pending` 的记录，插入下载队列
2. **下载**：限并发 2，带上简单 UA，失败重试；下完算 md5 比对，命中已有存储则直接复用 `stored_key`
3. **转码**：GIF 保留原格式（动图不能转静态），其余转 WebP，长边压到 1600px

转码工具用 `sharp`，Node 生态里最稳的，不依赖系统装 ffmpeg。

存储放对象存储（Cloudflare R2 免出口流量费，或国内 OSS 便于备案），库里只存 key。

## 六、服务与前端

### API

| 接口                                             | 用途                                   |
| ---------------------------------------------- | ------------------------------------ |
| `GET /api/members`                             | 成员列表，按团体分组                           |
| `GET /api/members/:id/messages?before=&limit=` | 时间线分页，游标用 msg_time                   |
| `GET /api/members/:id/images?before=`          | 图片墙                                  |
| `GET /api/search?q=`                           | 全文检索，PG 用 `pg_trgm`，量大再上 Meilisearch |
| `GET /api/stats`                               | 站点统计，展示抓取进度                          |

全部只读，无需登录。

### 前端

Next.js，成员页走 ISR（60 秒重新验证），兼顾 SEO 和「新消息较快出现」。

页面就四个：成员列表、成员时间线、图片墙、搜索结果页。时间线按日期分组，图片点击开灯箱。

样式保持极简——这类站的内容本身是主角，花哨的 UI 反而碍事。

## 七、部署

单机 Docker Compose，一台 2C4G 国内 VPS 足够（`pocketapi.48.cn` 国内直连，不需要代理）。

| 容器        | 作用              |
| --------- | --------------- |
| postgres  | 数据              |
| collector | 采集 + 图片管道       |
| web       | Next.js         |
| caddy     | 反向代理 + 自动 HTTPS |

备份策略：PG 每日 `pg_dump` 到对象存储，保留 7 天。图片本身在对象存储，不需要额外备份。

## 八、分期计划

| 阶段 | 内容                        | 出口标准                |
| -- | ------------------------- | ------------------- |
| P1 | 采集器（历史 + 增量）+ 入库 + 失效房间剔除 | 3 个成员的数据能稳定落库，重启可续传 |
| P2 | 图片管道（下载 + WebP + 对象存储）    | 图片能完整展示，存储体积符合预期    |
| P3 | API + 前端四个页面              | 站点可访问，时间线和搜索可用      |
| P4 | 全量灌入 + 增量守护 + 监控告警        | 350 个房间历史补齐，增量无缺口   |

不建议跳过 P1 直接铺量：管道有问题时，5 天的数据会全白跑。

## 九、风险

| 风险     | 应对                                             |
| ------ | ---------------------------------------------- |
| 账号被封   | 单账号限速保守（5s）；准备 1–2 个备用号；token 失效可自动告警          |
| 接口变更   | 48tools / yaya_msg 是活的参照系，定期比对；解析层做宽松处理，未知字段保留 |
| 图片域名失效 | `src_url` 原样保留，转码后以自有存储为准，不依赖源站                |
| 存储增长   | WebP + md5 去重双重控制；监控月增量                        |
| 法律风险   | 见下节                                            |

## 十、合规边界

这部分不是免责声明，是产品约束，需要写进实现：

- 粉丝发言展示时只显示昵称，用户 ID 存哈希，不落明文
- 图片转码时剥离 EXIF（原图可能带拍摄设备信息）
- 提供 `robots.txt` 和 takedown 联系方式，收到下架通知即处理
- 不提供全站批量导出功能
- 不做任何形式的付费或广告变现

这些动作不能消除侵权风险，但能把「恶意聚合」的性质变成「被动归档」，处理起来完全不同。

## 附：待验证项

1. **间隔下限**：2 秒是否安全（决定全量从 5 天压到 2 天的可能性）
2. **回溯极限**：能否翻到 3 年以上，还是服务端有窗口限制
3. **token 有效期**：多久失效一次，决定自动重登策略
