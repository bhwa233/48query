# 48query 数据获取能力与每日跑批方案

> 整理日期：2026-10-18
>
> 文档状态：方案讨论稿，尚未进入业务代码实现
>
> 采集原则：每日跑批、次日更新；网站访问只查询本站数据，不触发上游采集

## 1. 结论

48query 可以采用每日跑批的方式，优先建设房间消息统计与检索、录播目录与弹幕统计、鸡腿榜档案。

不同数据需要采用不同的统计方式：

- **历史事件**：房间消息、动态、平台仍保留的录播与弹幕，可以尝试分页补采，再按事件发生时间汇总。
- **状态快照**：粉丝数、当前榜单值等，需要每天保存采集时的状态；通常无法补出开始采集前每一天的变化。
- **实时过程**：在线人数曲线、未保存的房间上麦音频等，现有证据不足以支持事后还原，不作为每日跑批的承诺范围。

“接口有实现”不等于“当前接口已验证可用”，也不等于“能获得全历史、全用户、全字段”。网站应明确展示数据截止时间、覆盖范围和缺失状态。

### 3.1 房间消息的统计口径

至少分清以下三个维度：

- **房间维度**：消息出现在哪位成员的房间。
- **发送者维度**：消息由房间主人、其他成员、粉丝还是系统发送。
- **内容维度**：主动发言、公开回复、图片、音频、视频、直播通知等。

例如，其他成员在某人的房间发言，应保留实际发送者，不能计为房间主人的本人消息。直播通知等系统内容也不应默认计入本人主动发言量。

48tools 会按 `roleId === 3` 过滤部分成员消息，但角色只能作为辅助依据。是否为房间主人，应结合稳定用户 ID 与房间所属成员 ID 判断。

### 3.2 录播弹幕的能力边界

48tools 的录播弹幕解析格式为“相对时间、昵称、文本”。解析结果中没有稳定用户 ID，也没有完整礼物流水结构。

因此可以做：弹幕文本搜索、弹幕条数、每分钟弹幕量、关键词和不同昵称数。不能直接做：真实独立观众数、跨场次独立用户数、全量送礼明细或用户消费画像。

相同昵称可能属于不同用户，同一用户也可能改名。“不同昵称数”必须以这个名称展示，不能标为独立用户数。

## 4. 有获取线索，但需验证后才能作为正式指标的数据

| 数据或指标 | 现有线索 | 每日跑批的处理方式 | 验证重点 |
| --- | --- | --- | --- |
| 粉丝数、关注数 | yaya_msg 主页读取相关字段，并兼容多个字段名 | 有效后每日保存快照，计算相邻快照净变化 | 成员账号是否稳定返回、数值含义、精度；历史日变化是否另有来源 |
| 直播贡献榜 | `getLiveRank` 返回用户和 `money` 等字段，界面展示排名 | 尝试按场次保存结束后的榜单 | 历史场次是否可查、返回条数、是否截断、数值单位、是否为最终值 |
| 直播人气值 | 详情读取 online、hot、popularity 等候选字段 | 保留原始字段与采集时间，确认含义后展示 | 人气、播放量与真实观众数的区别；是否随回放继续增长 |
| 成员直播时长 | 有 `/live/api/v1/live/result` 封装，未找到完整结果解析证据 | 优先验证可靠起止时间；媒体推算结果另标为录播时长 | 字段、时间单位、结束状态、是否含中断或剪辑 |
| 动态点赞数、评论数 | 有帖子详情和一级评论列表接口 | 若计数有效则保存快照，并回查旧帖 | 不同帖子类型的字段、评论分页、删除影响、计数变化 |
| 用户回复／互动榜 | 回复消息中存在目标信息，部分统计使用昵称映射用户 ID | 优先按稳定 ID 汇总；只有昵称时保留未确认对象 | 同名、改名、目标 ID 是否存在，不能凭昵称强行合并 |
| 鸡腿历史期次及日期 | 部分期次使用连续 rankId 枚举，部分日期按周推算 | 仅将真实返回或另有证据的期次与日期视为已确认 | ID 是否连续、期次是否缺失、推算日期是否正确 |

### 4.1 贡献值不直接等于收入

yaya_msg 的界面会将返回榜单中的 `money` 相加，显示“总贡献值”。如果接口只返回部分用户，求和结果只是返回榜单的贡献值合计。

在返回范围和单位验证前，不称其为整场总流水，也不换算为人民币收入。当前礼物目录价格不能直接套用于历史礼物，实际结算收入也不能由礼物展示值推断。

### 4.2 公开翻牌记录不等于全部翻牌业务

yaya_msg 的历史翻牌分析来自当前登录账号的提问记录，可使用其中的提问时间、回答时间和花费字段。这个数据范围不能推广到全体粉丝。

公开消息能够支持“采集到的公开翻牌记录数”。全体提问数、成员整体回答率、整体平均回复耗时和全部翻牌收入，目前均不能承诺。

## 5. 每日跑批无法还原或当前不能承诺的数据

| 数据 | 当前判断 |
| --- | --- |
| 实时在线曲线、最高同时在线人数、每分钟人气变化 | 未找到可补取这些历史序列的实现；每天一次取值不能还原过程 |
| 每场真实独立观众数、跨场次观众去重 | 弹幕只能证明发言行为，不能覆盖沉默观众；人气字段也不能直接替代 |
| 跨场次独立弹幕用户数 | 现有录播文本解析缺少稳定用户 ID，按昵称无法准确去重 |
| 完整礼物流水、每次送礼时间、完整种类和数量、真实收入 | 实时消息类型中有礼物字段，但未找到同等完整的历史流水实现；贡献榜与礼物回复不能替代 |
| 已结束且没有平台回放的房间上麦音频 | 参考项目通过查询当前上麦状态后实时录制，每日跑批无法补录；与有录播的直播电台分开处理 |
| 全体粉丝的私信、全部翻牌提问及回答 | 对应查询依赖当前登录账号，不能据此建立全站数据集 |
| 成员真实在线时长、打开 App 次数、阅读了哪些消息 | 消息时间只能证明发送行为，本次未找到这些行为数据的接口 |
| 两次跑批之间出现又删除、且平台不再返回的内容 | 可能完全漏掉，无法保证恢复 |
| 任意账号均可获取的全部内容 | 登录状态、房间状态及访问权限会影响范围 |
| 开始采集前每天的粉丝增减、榜单过程变化 | 当前值或最终榜单通常不足以重建历史过程 |

## 6. 每日跑批方案

### 6.1 时间与展示规则

- 按北京时间 `Asia/Shanghai` 划分自然日。
- 每日启动一次主批次；具体启动时刻、目标完成时刻和重试预算待定。
- 网站正式日统计默认截止到前一日，批次完成后更新；不保证零点即出最终数据。
- 用户打开页面、切换筛选或刷新页面，只查询本站存储，不触发上游采集。
- 每条快照保存实际采集时间。不同成员的快照不假定采于同一时刻，也不能标成精确的零点状态。

### 6.2 批次流程

1. **更新基础资料**：读取成员目录和房间映射，保存本次有效版本。当前所属团体与历史事件所属团体的口径分开。
2. **获取每日新增事件**：各房间从最新记录向前翻页，直到覆盖上次成功位置。一天超过一页时继续获取，不能每天只取最新一页。
3. **保存记录与采集进度**：按稳定标识去重，每页持久化后更新进度；异常中断后可以续跑。同一时间戳下的多条记录不能被截断。
4. **发现新增录播与获取弹幕**：分页读取录播，查询详情，将可用弹幕文件加入独立任务。未生成文件的场次在后续批次重试，无需下载整场视频。
5. **采集榜单与状态快照**：保存榜单期次、原始数值、采集时间和响应范围。粉丝数等通过验证后加入此步骤。
6. **回查近期数据**：设置可配置的回查窗口，处理延迟生成的录播、跨午夜结束的场次、榜单结算和动态计数变化。窗口长度在验证后决定。
7. **生成并发布汇总**：按事件时间计算日统计，记录各数据源的成功与失败状态，再发布批次结果。

### 6.3 首次历史补采

历史补采独立于每日新增任务，按成员、房间、录播和榜单分别保存游标与覆盖范围，可以分多天完成。每日新增采集优先，避免为了补旧数据错过新数据。

请求采用全局限速、有限重试和退避。具体速率需依据后续验证确定，不能将参考代码的请求间隔或短时探测成功率当作长期可用速率。

原实施计划中“约 350 个房间、每次请求间隔 5 秒”的假设，单轮每房间一页就约需 29 分钟，尚未计入翻页、网络耗时、重试和其他数据源。每日跑批允许较长执行窗口，但仍需要控制总请求量。

### 6.4 失败、缺失与数据修订

- **零与未知分开**：任务失败或历史未补齐，不能显示为零消息、零弹幕或零贡献。
- **记录覆盖范围**：保存每个房间的最早可用记录、已覆盖时间段、是否到达上游末尾及最后成功采集时间。“到达末尾”也不代表平台未删除过记录。
- **允许迟到数据修订**：后续批次发现旧日期的新记录或修正字段后，重算受影响的统计。
- **不凭列表缺失认定删除**：单次没有返回某记录，可能是分页或权限变化；不直接据此删除本地记录。
- **跨午夜直播单独处理**：场次按开播日归属，或按实际时长拆分到各日，需统一口径；没有可靠起止时间时不做时长拆分。
- **同范围比较**：历史覆盖不同的成员不能直接用不加说明的累计总量排名；应限制共同时间范围或明确标注覆盖差异。

## 7. 建议的第一期范围

以下为建议范围，尚未作为最终开发清单确认。

| 模块 | 建议纳入 | 暂不承诺 |
| --- | --- | --- |
| 房间统计与检索 | 本人消息量、活跃天数、类型分布、发送时段、公开回复／翻牌记录、图片时间线、全文搜索 | 全体粉丝完整发言史、整体翻牌回答率、真实在线时长 |
